Yes. I would introduce the **limitations in Class 1**, but **not teach the solutions in depth there**.

Pedagogically, this creates a strong narrative:

> **Class 1: What GenAI is → why it is powerful → why it is not enough by itself.**
> **Classes 2–3: How we overcome those limitations and build useful AI systems.**

That also gives students a reason to care about concepts like RAG, context engineering, tools, agents, harnesses, evals, and human oversight later.

## Class 1 — UNDERSTAND

### What is AI, what changed with GenAI, and what are its limits?

After explaining LLMs, tokens, training, inference, etc., add:

### The fundamental limitations of GenAI

Keep these at the **intuition level**.

| Limitation                                         | Executive intuition                                          | Example                                       |
| -------------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------- |
| **Hallucination**                                  | Fluent ≠ correct                                             | Invented fact, source or policy               |
| **Knowledge cutoff / freshness**                   | The model was trained in the past                            | “What are today's sales?”                     |
| **No proprietary knowledge by default**            | The model doesn't automatically know your organization       | Internal procedures, contracts, customer data |
| **Limited context**                                | It cannot consider unlimited information at once             | Thousands of company documents                |
| **Probabilistic behavior**                         | Same task doesn't behave exactly like deterministic software | Slightly different answers                    |
| **Reasoning limitations**                          | Models can make convincing logical mistakes                  | Financial calculation or complex planning     |
| **No inherent access to systems**                  | Knowing something ≠ being able to do something               | “Refund this customer”                        |
| **No persistent organizational memory by default** | A model isn't automatically your company's memory            | Previous cases or customer interactions       |
| **Security / privacy**                             | Context may contain sensitive information                    | Customer or strategic data                    |
| **Control / autonomy**                             | More ability to act creates new failure modes                | Agent sends an incorrect payment              |

Then give them one important mental model:

> **LLMs are powerful general-purpose intelligence components, not complete enterprise systems.**

That sentence sets up the rest of the course.

## But introduce the solutions only briefly

At the end of Class 1, show a **“limitation → solution” preview**, without teaching the technologies yet.

```text
LLM LIMITATION                    SYSTEM RESPONSE

Doesn't know our data       →     Context / RAG
Knowledge may be outdated   →     Search / APIs / Tools
Can hallucinate             →     Grounding / Evals / Human review
Limited context             →     Retrieval / Context Engineering
Cannot take action          →     Tools / Agents
No persistent state         →     Memory
Probabilistic               →     Evals / Guardrails / Workflows
Sensitive information       →     Security / Permissions / Governance
Uncontrolled autonomy       →     Workflows / Human-in-the-loop
```

Tell students:

> “Today you only need to understand **why these problems exist**. In Class 3, we'll see how modern AI systems are designed around them.”

This creates anticipation rather than cognitive overload.

# Then progressively resolve them

I'd actually use the limitations as a **thread across all four classes**.

### Class 1 — UNDERSTAND

**Model and limitations**

```text
LLM
 │
 ├── powerful
 │
 ├── general purpose
 │
 └── limited
      ├─ hallucinations
      ├─ outdated knowledge
      ├─ no enterprise context
      ├─ limited context
      └─ cannot inherently act
```

The executive leaves thinking:

> *“An LLM is impressive, but it isn't an enterprise solution.”*

### Class 2 — IMAGINE

**Capabilities**

Now show what models can nevertheless provide:

```text
Understand
Generate
Extract
Search
Reason
Recommend
Create
```

Across:

**Text + Image + Audio + Video + Code + Data**

The executive leaves thinking:

> *“I can recognize which AI capabilities could change a business process.”*

Now return explicitly to Class 1:

## I would make “Problem → Solution” a recurring teaching device

For example:

### Problem: Fresh information

> “Who is our largest customer this month?”

The LLM cannot inherently know.

**Solution:**

```text
LLM → Tool → CRM / Database → Current data → LLM → Answer
```

### Problem: Proprietary knowledge

> “What is our policy for approving contracts over €1M?”

**Solution:**

```text
Question
   ↓
Retrieve internal policy
   ↓
Give relevant context to LLM
   ↓
Answer grounded in policy
```

→ **RAG / Context Engineering**

### Problem: Taking action

> “Reschedule my customer meeting.”

LLM understands the request but cannot inherently change the calendar.

```text
LLM
 ↓
Tool
 ↓
Calendar API
 ↓
Action
```

→ **Tool use / Agents**

### Problem: Hallucination

For a high-risk process:

```text
AI generates
     ↓
Evaluation / Validation
     ↓
Human approval
     ↓
Action
```

→ **Evals + guardrails + human-in-the-loop**

This is exactly the kind of cause-and-effect understanding executives need.

## One addition to Class 1: “What LLMs are NOT”

I think this would be particularly valuable for low-tech executives.

A short slide:

### An LLM is not...

**A database** — it doesn't retrieve facts the same way a database does.

**A search engine** — although it can be combined with search.

**Always up to date** — unless connected to current information.

**Your company's knowledge base** — unless provided access to that knowledge.

**Deterministic software** — outputs are probabilistic.

**An agent by itself** — a model generating text is not the same as a system capable of acting.

**Automatically trustworthy because it sounds confident** — linguistic fluency and factual correctness are different things.

Then:

### So why is it transformative?

Because a single general-purpose model can:

**understand + generate + reason + transform + interact across many modalities and domains.**

And when connected to:

**Context + Knowledge + Tools + Workflows + Systems**

it becomes dramatically more useful.

That creates the conceptual tension you want:

> **GenAI is simultaneously extraordinarily capable and fundamentally limited.**

Understanding **both sides** is one of the most important intuitions an executive should leave the first class with.
