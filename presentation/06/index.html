Objective

Understand what a harness is: the layer around a GenAI model that contextualizes, extends, coordinates, constrains and operationalizes it. Harness

The components of a harness

A harness turns a model into a working system through five building blocks.

  • Context and knowledge integration

    What the model sees: instructions, documents and retrieved data.

  • Memory and state management

    What persists across steps, turns and sessions.

  • Tools and external capabilities

    Actions beyond text: search, code execution and APIs.

  • Orchestration and control

    Loops, workflows, routing, permissions and guardrails.

  • Evaluation mechanisms

    Tests, metrics and feedback that check and improve outputs.

Harness

Three layers, three roles

  1. 1 · ModelModels are the intelligence

    They provide the reasoning, understanding, and generation capabilities.

  2. 2 · HarnessThe harness is the system around the intelligence

    It orchestrates models, tools, context, and workflows to turn intelligence into reliable applications.

  3. 3 · Context & knowledgeContext & knowledge provide what the intelligence needs

    They ground the model in relevant data, memory, and knowledge to produce meaningful, context-aware responses.

Note: "intelligence" and "thinks" are shorthand. Models generate from learned patterns; they don't think the way people do. And context is more than knowledge: it also carries instructions, goals, and the current state of the task.

Continuous improvement

Four Dimensions of Continuous Improvement

  1. Model Optimization Techniques

    Improve model capabilities, alignment, efficiency, and task-specific performance through model selection, configuration, and adaptation.

  2. Harness and Capability Extension

    Extend and control model behavior through context, knowledge, memory, tools, orchestration, and runtime mechanisms.

  3. Experimentation and Validation

    Systematically test and compare models, prompts, contexts, tools, and system configurations to validate performance and guide design decisions.

  4. Observability and Continuous Improvement

    Monitor real-world behavior, identify limitations and failure modes, and use evidence to guide ongoing improvements.

Continuous improvement

An Interconnected Improvement System

  • Systemic perspective

    Improving GenAI performance requires coordinated interventions across the model, harness, and system configuration.

  • Evidence-driven decisions

    Experiments and production observability reveal what works, what fails, and what needs improvement.

  • Iterative evolution

    Feedback loops connect evaluation, adaptation, and deployment, enabling GenAI systems to continuously improve over time.

Key takeawayImproving GenAI systems is not about optimizing the model alone. It is about continuously improving the entire system.

Continuous improvement

Why Model Optimization Alone Is Not Enough

Model optimization can improve capabilities, but it cannot address all the limitations of GenAI systems.

  • Cost and complexity

    Fine-tuning and other optimization techniques can require substantial computational resources, specialized expertise, high-quality data, and ongoing maintenance.

  • Knowledge limitations

    Model optimization alone does not provide reliable access to up-to-date, proprietary, or task-specific contextual information.

  • Memory limitations

    It does not inherently provide persistent memory, long-term state management, or overcome context-window constraints.

  • Capability limitations

    Models still need external tools to retrieve information, perform precise computations, interact with systems, and execute actions.

  • Reliability limitations

    Optimization does not eliminate hallucinations, reasoning errors, or the need for runtime controls and validation.

Key takeawayModel optimization improves what a model can do; the harness extends what the system can access, remember, control, and execute.

Continuous improvement · Summary

Main takeaways

  1. Leave model training to the frontier labs

    Building a new foundation model, or training one further, is frontier-lab work that costs tens to hundreds of millions. And training alone can’t fix knowledge cut-offs, memory, actions or hallucinations.

    Grok 4 ≈ $490M per training run. OpenAI: accuracy will never reach 100%
  2. The harness can matter more than the model

    Context, memory, tools, orchestration and guardrails expand and control what the model can do. The same model performs very differently in a different harness.

    GPT-5 on Terminal-Bench 2.0: 33.9% → 49.6%, changing only the harness
  3. Improve continuously, with evidence

    Building and maintaining a GenAI system is a loop. Invest in experiments and observability, and let feedback, data and facts drive each change.

    Read real traces → find failure modes → fix → measure again

Context

What is context?

Everything the model sees when it generates a response: the tokens in its context window.

Context window · a finite token budget
System instructions User input Conversation history Retrieved knowledge Tool results Memory & state
Weights + context are all it knows

At inference, the model can only use what it learned in training and what is in the window.

The window is finite

Every token competes for space and for the model’s attention.

More is not better

Accuracy drops as inputs grow longer (“context rot”), so relevance beats volume.

Sources: Anthropic, Effective context engineering for AI agents (2025); Chroma Research, Context Rot (2025).

Context · Summary

Main takeaways

  1. Your context is your competitive edge

    Everyone can use the same frontier models. Only your organization has its data, processes, rules and know-how. The better that context is curated, structured and kept current, the better the outcomes.

    Top foundation models now score within a few points of each other on common benchmarks
  2. Context engineering builds runtime infrastructure

    Its outputs (knowledge bases, schemas, prompts and skills, rules, retrievers and memory) are assets the harness draws on at every step, giving the model the right information, in the right format, at the right time.

    “Building dynamic systems to provide the right information and tools in the right format.” H. Chase, LangChain

Tools

A trained model has four gaps

It is a frozen set of weights that predicts the next token. Tools fill what that design leaves out.

GapFresh information

Training stopped at a cutoff date.

Weather API, web search
GapReliable computation

Calculator, code
GapPrivate data

Your data was never in its training set.

Database, internal API
GapThe ability to act

Text alone changes nothing in the world.

Create ticket, send email
Tools

The tool loop

A tool is a function in your program, described to the model by a name, a purpose and its arguments.

1 · Your codesends the question and the tool descriptions
2 · Modelreplies with a request:
get_temperature(city="Lisbon")
3 · Your coderuns the function and sends back the result: 19.4 °C
4 · Modelanswers in text:
“It is 19.4 °C in Lisbon.”

Steps 2–3 repeat until the model replies with text instead of a tool call. Agent frameworks add features around this loop; the core is these few lines.

The model never runs anything. A tool call is structured output. Your code executes it, so control lives in that gap.

Tools

The model only reads the description

# What the model sees: never the Python code
{
  "name": "get_temperature",
  "description": "Current air temperature
     in °C for a city. Use for questions
     about today's weather.",
  "parameters": {
    "city": { "type": "string" }
  }
}
  1. Choice comes from text. The model picks a tool and fills its arguments from the name and description alone.
  2. Nothing maps the question to the function. The model extracted city="Lisbon" itself.
  3. Write descriptions with care. They guide the model; they don’t guarantee what it does.

How LLMs use tools

Notebook notebooks/llm_tools_01.ipynb asks the same question twice: once to a model on its own, once to a model with tools.

OPENAI_API_KEYTAVILY_API_KEY for example 2~70 cells

The whole mechanism

The loop below is all there is. The model returns either text or a request to call a tool; your code runs the tool and sends the result back.

messages = [{"role": "user", "content": question}]
while True:
    reply = model(messages, tools=TOOL_DESCRIPTIONS)
    if not reply.tool_calls:
        return reply.text                      # done: an answer in text
    for call in reply.tool_calls:
        result = TOOLS[call.name](**call.arguments)   # your code runs it
        messages.append(tool_result(call.id, result))

The five examples

1. Temperature: fresh information

Without tool

The model can’t know today’s value. It declines, or offers a typical figure for the season.

With tool

It calls get_temperature with city="Lisbon". Our code calls Open-Meteo; the model only turns the JSON into a sentence.

2. Temperature + activities: chained tools

The second tool needs the first tool’s result. Our code never connects them: the model passes temperature_c from one call to the next because the description says it needs it.

3. Search: open-ended

Asked about an event after its training cutoff, a model without tools may even insist it hasn’t happened yet: its sense of “now” is frozen. With search it writes its own query and answers from the article. The answer is only as good as the source.

4. Calculator: reliable computation

The tool computes; the model only sets up the call. The notebook checks the result against the formula. Note that calculate does not use eval: arguments come from the model and are untrusted.

5. Private data and actions

The model looks up an order that exists only in our (fake) data, and can take an action. This is where permission checks matter most.

  1. Run Example 1 for your own city. Read the trace: which arguments did the model choose?
  2. Rewrite a tool description to be vague. Does the model still call it, or call it correctly?
  3. Ask a question none of the tools covers. Does the model call a tool anyway?

Takeaways

  1. The model requests, your code executes. A tool call is structured output, not execution.
  2. The loop is small. Send the question and tools, run what is asked, send results back, repeat.
  3. Descriptions are prompts. The model chooses tools from their names and descriptions.
  4. Tool arguments are untrusted input. Validate them as you would any external request.
  5. Tool results are untrusted too. A web page could contain text that tries to instruct the model.
  6. Separate reads from writes. For tools that change state, add permission checks or human confirmation in code, not only in the description.
Tools · Takeaways
