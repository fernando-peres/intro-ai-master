Unit 1 · Embeddings

Closeness is useful

Similarity is usually measured with cosine similarity: near 1 means the same direction, near 0 means unrelated.

Semantic search

“refund for a broken bike” finds “return policy for damaged items”.

Retrieval for RAG

Embed the question, fetch the closest passages, give them to the model as context.

Clustering

Group tickets, reviews or documents by topic without labels.

Deduplication & recommendations

Find near-duplicates, or items similar to what a user liked.

Similar is not the same as true. Embeddings find related text. Whether that text answers the question is for the model, and your evals, to decide.
Unit 1 · Hands-on

Embeddings in a few lines

Notebook notebooks/embeddings_01.ipynb turns five sentences into vectors, compares them, and plots them.

Pythonsentence-transformersruns locally, no API key

1. Load a model and encode sentences

The model all-MiniLM-L6-v2 is small and runs on a laptop. Each sentence becomes a vector of 384 numbers.

from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")
sentences = [
    "The cat is sleeping on the couch.",
    "A dog is lying on the couch.",
    "The car is red.",
    "I love programming with Python.",
    "The sofa is comfortable.",
]
embeddings = model.encode(sentences)   # shape: (5, 384)

2. Compare every pair

Cosine similarity compares the direction of two vectors. The notebook prints it for every pair of sentences.

from scipy.spatial.distance import cosine

sim = 1 - cosine(embeddings[0], embeddings[1])   # cat/couch vs dog/couch

What to look for: the two couch sentences score high with each other, and the sofa sentence is closer to them than to the car or to Python. No words need to match: “couch” and “sofa” are different words with close meanings.

3. Plot the meaning space

384 dimensions can't be drawn, so the notebook reduces them to 2 with PCA (and t-SNE as an alternative). Related sentences cluster; unrelated ones are far apart.

  1. Add a sentence of your own, such as "The kitten naps on the armchair." Predict where it lands, then run the cells.
  2. Add a sentence in Portuguese. Does this model place it near its English equivalent? (This model is trained mostly on English; multilingual models exist.)
  3. Add two sentences with the same words in a different order and opposite meaning. How close are they?

Unit 2 · Tools

The tool loop

A tool is a function in your program, described to the model by a name, a purpose and its arguments.

1 · Your codesends the question and the tool descriptions
→
2 · Modelreplies with a request:
get_temperature(city="Lisbon")
→
3 · Your coderuns the function and sends back the result: 19.4 °C
→
4 · Modelanswers in text:
“It is 19.4 °C in Lisbon.”

Steps 2–3 repeat until the model replies with text instead of a tool call. Agent frameworks add features around this loop; the core is these few lines.

The model never runs anything. A tool call is structured output. Your code executes it, so control lives in that gap.
Unit 2 · Tools

The model only reads the description

# What the model sees: never the Python code
{
  "name": "get_temperature",
  "description": "Current air temperature
     in °C for a city. Use for questions
     about today's weather.",
  "parameters": {
    "city": { "type": "string" }
  }
}
  1. Choice comes from text. The model picks a tool and fills its arguments from the name and description alone.
  2. Nothing maps the question to the function. The model extracted city="Lisbon" itself.
  3. Write descriptions with care. They guide the model; they don't guarantee what it does.

Unit 2 · Hands-on

How LLMs use tools

Notebook notebooks/llm_tools_01.ipynb asks the same question twice: once to a model on its own, once to a model with tools.

OPENAI_API_KEYTAVILY_API_KEY for example 2~70 cells

The whole mechanism

The loop below is all there is. The model returns either text or a request to call a tool; your code runs the tool and sends the result back.

messages = [{"role": "user", "content": question}]
while True:
    reply = model(messages, tools=TOOL_DESCRIPTIONS)
    if not reply.tool_calls:
        return reply.text                      # done: an answer in text
    for call in reply.tool_calls:
        result = TOOLS[call.name](**call.arguments)   # your code runs it
        messages.append(tool_result(call.id, result))

The five examples

1. Temperature: fresh information

Without tool

The model can't know today's value. It declines, or offers a typical figure for the season.

With tool

It calls get_temperature with city="Lisbon". Our code calls Open-Meteo; the model only turns the JSON into a sentence.

2. Temperature + activities: chained tools

The second tool needs the first tool's result. Our code never connects them: the model passes temperature_c from one call to the next because the description says it needs it.

3. Search: open-ended

Asked about an event after its training cutoff, a model without tools may even insist it hasn't happened yet: its sense of “now” is frozen. With search it writes its own query and answers from the article. The answer is only as good as the source.

4. Calculator: reliable computation

The tool computes; the model only sets up the call. The notebook checks the result against the formula. Note that calculate does not use eval: arguments come from the model and are untrusted.

5. Private data and actions

The model looks up an order that exists only in our (fake) data, and can take an action. This is where permission checks matter most.

  1. Run Example 1 for your own city. Read the trace: which arguments did the model choose?
  2. Rewrite a tool description to be vague. Does the model still call it, or call it correctly?
  3. Ask a question none of the tools covers. Does the model call a tool anyway?

Takeaways

  1. The model requests, your code executes. A tool call is structured output, not execution.
  2. The loop is small. Send the question and tools, run what is asked, send results back, repeat.
  3. Descriptions are prompts. The model chooses tools from their names and descriptions.
  4. Tool arguments are untrusted input. Validate them as you would any external request.
  5. Tool results are untrusted too. A web page could contain text that tries to instruct the model.
  6. Separate reads from writes. For tools that change state, add permission checks or human confirmation in code, not only in the description.
Unit 2 · Takeaways

Tools give reach. Code keeps control.

  1. The model requests, your code executes.
  2. The loop is small: ask, run, return, repeat.
  3. Descriptions are prompts. Write them with care.
  4. Arguments are untrusted input. Validate them.

03

MCP: one plug, many systems

The Model Context Protocol standardises where tools come from and who runs them.

N × M → N + MHost, client, serverDiscoveryLeast privilege
Unit 3 · MCP

From N × M integrations to N + M

An open standard introduced by Anthropic in 2024, often called “USB-C for AI”.

Without a standard · every app builds every connector: 4 × 5 = 20

With MCP · each app has one client, each system one server: 4 + 5 = 9

Unit 3 · MCP

The moving parts

RoleWhat it is
HostThe application the user works in: a chat app, an IDE, a notebook
ClientHolds one connection to one server, inside the host
ServerA program exposing capabilities: fetch a URL, read files, query a CRM
A server offersWho decides to use it
ToolsThe model · fetch(url)
ResourcesThe application · a file or a schema to attach as context
PromptsThe user · a reusable template, like a slash command
MCP does not replace function calling. The model still uses ordinary tool calls. MCP standardises where the functions come from, and the host still runs them.
Unit 3 · MCP

When to use it, and when not to

Use MCP when
  1. Several apps or agents need the same integration
  2. You want existing servers instead of writing connectors
  3. Tools should be discoverable at runtime
Skip it when
  1. One script needs one function: plain function calling is simpler
  2. A fixed API call is enough and no model has to choose
  3. Each extra tool schema adds cost you can't justify
Unit 3 · Takeaways

Before you connect a new server

It runs with your permissions, and the model will read whatever it returns.

1

Trust

Do you trust who wrote it?

2

Discover

List its tools, resources and prompts. Don't trust the README.

3

Restrict

Offer the model only the tools it needs. Scope folders and accounts.

4

Test

Try it with the MCP Inspector before a model uses it.

A small MCP client

Everything MCP-specific fits in one cell, with three functions:

  1. connect starts a server and performs the MCP handshake.
  2. to_openai_tools translates MCP tool definitions into the function-calling format the model understands.
  3. ask_with_mcp runs the same loop as Unit 2: the model requests a call, the client runs it on the server, the result goes back.

Messages are JSON-RPC 2.0, over stdio for local servers (the host starts the server as a subprocess) or Streamable HTTP for remote ones.

Example 1: the Fetch server

The question: the latest release of a package on PyPI, something that changes often and can be checked independently.

Without MCP

Even with the exact URL in the prompt, the model can't open it. At best it says so; at worst it offers a remembered version number that sounds current.

With MCP

Same model, question and system prompt. It calls fetch, which it learned from the server's own tool description, and answers from the page.

Check the facts outside the model. The notebook fetches the feed itself and scores both answers against it. A confident answer is not evidence.

What it cost: the tool schema, the returned page and a second model call, all in tokens. And a new risk: the model now reads text strangers wrote, so the system prompt tells it to treat tool output as data. That reduces prompt injection; it doesn't eliminate it.

Asking a server what it can do

Discovery is part of the protocol, so you never have to guess.

QuestionMCP method
Who are you, and what do you support?initialize
Which actions can the model take?tools/list
Which data can the application attach?resources/list
Which templates can the user pick?prompts/list

Declared does not mean available. Run the list query and handle the error -32601 (method not found). For a visual view, use the MCP Inspector.

Example 2: the Filesystem server

The same client, unchanged, now talks to a second server. This is the point of a standard. The notebook then limits what the model may touch: the server is scoped to one folder, and the client offers only the tools the task needs. Afterwards it checks the disk, not the model's claims.

  1. Run the four discovery queries on the Fetch server. Which capabilities does it declare but not provide?
  2. Remove the write tools from the filesystem client. Ask the model to create a file. What does it say?

Takeaways

  1. MCP changes a model's reach, not its intelligence.
  2. It is a standard, not a tool: one client worked with both servers.
  3. The model requests and the host executes. Control lives in that gap.
  4. Capabilities are discoverable, and declared does not mean available.
  5. Verify with a source outside the model: facts and disk state, not claims.
  6. Grant the least privilege. Scope the server and filter tools in the client.
  7. Every connection has a price in tokens, time and prompt-injection exposure.

Learn more: modelcontextprotocol.io, including the specification and the reference servers.

Unit 4 · Skills

Progressive disclosure

Why not put every procedure in the system prompt? With dozens of them, every request would pay for instructions it doesn't need.

Stage 1 · always

Catalog

Each skill's name and one-line description. A few lines for the whole library.

Stage 2 · when it applies

Procedure

The full SKILL.md, loaded when the model decides the skill fits the task.

Stage 3 · if needed

References

Extra files inside the skill: limits, templates, tables. Read only when the procedure calls for them.

The description decides. The model picks a skill from its description alone, so write it for that choice.

Example 1: a late order

The tools can already do everything: look up the order, create a ticket, issue a voucher. What they can't supply is the company's rules: which priority, whether a voucher is allowed, how much, and how the ticket must be written.

Tools only · 0 of 4 checks

Looked up the order, then stopped and offered to help. Nothing told it it was allowed to act. Another run might act, but priority, format and amount would be guesses.

Picked late-order from its description, loaded it and followed each step. The ticket summary matches the required format exactly.

Example 2: an expense review

The company's limits live in a reference file, so the model must go through all three stages. No model could know these limits.

When a skill should not load

Given a question no skill covers, the model loaded no skill and called no tool. Stage 1 cost only a few catalog lines.

  2. Make a skill's description vague. Does the model still pick it?
  3. Write a third skill for a procedure from your own work, in plain language.

Takeaways

  1. Tools give ability, skills give know-how. The model needed both.
  2. A skill is just text plus a way to read it.
  3. Progressive disclosure keeps context small, so a large library stays cheap.
  4. The description decides which skill loads.
  5. Skills guide, code enforces. If a voucher must never exceed 10 USD, check it inside issue_voucher too.
  6. Skills are instructions, so trust matters. Only load skills from sources you trust.

A judge is a model too

It can be fooled, it can be inconsistent, and it can be measured.

Bias

Position

Prefers the answer shown first (or second). Pairwise comparisons need both orders.

Bias

Verbosity

Rewards longer answers that add nothing.

Attack

Prompt injection

The graded text tells the judge to pass it. Keep hard rules in code.

Noise

Inconsistency

The same input can get a different verdict on another run.

Judge the judge. A judge is only as trustworthy as you've measured it against human labels. Read the disagreements, improve the prompt, measure again.

Change the instruction

Feed in the critique, repair the draft, route by the failed criterion, or switch to a stronger model. Same instruction = rolling the dice again.

Set a limit

Some requests never pass. Write the fallback in advance. Each attempt adds cost and latency while the customer waits.

Fix the cause

A loop treats symptoms, and optimises for the judge it talks to. If it keeps fixing the same thing, fix the prompt or the retrieval.

An experiment: which variant is better?

  1. Fix the hypothesis and the metric first
  2. Build a dataset with hard segments; keep a split aside
  3. Run every variant on every case, several times
  4. Score with code first, then a measured judge
  5. Report intervals and paired tests, by segment
  6. Read the failures, including the dataset's own
  7. Improve, then confirm on the held-out split

In the notebook: 30 fake support cases, three prompts and an agent with a tool.

Explicit rules beat a minimal prompt

The one clear difference. Most failures were the wrong action: answer, refuse or escalate.

The rest: no evidence either way

“No significant difference” means no evidence, not “equal”. The dataset hit its ceiling: next step is harder cases.

Cost decides ties

Two variants used ~45% and ~75% more tokens. A win must pay for that.

Unit 5 · Hands-on

Evals and LLMs as judges

Four notebooks, each building on the last: a basic judge, what judges can check and where they fail, a judge inside the system, and a full experiment.

OPENAI_API_KEYoptional JUDGE_MODELevals_04 makes several hundred calls

evals_01 · Call a model, then evaluate it

Start with code where code works: required strings, formats, numbers. Then add a free-text judge, and then a judge with structured output, so code can use the verdict.

class Verdict(BaseModel):
    critique: str                      # reasoning first
    grounded: Literal["pass", "fail"]  # then named criteria
    complete: Literal["pass", "fail"]
    tone: Literal["pass", "fail"]

Grade named criteria rather than a general score, so a failure tells you what to fix. One verdict is an anecdote; a pass rate over a fixed set is a measurement.

evals_02 · What judges can check, and when to trust them

Part 1 runs eight checks, each with a passing and a failing case: groundedness, correctness, completeness, policy, tone, refusal, agent trajectory and pairwise comparison. The answers are written by hand, so we know which should pass.

Part 2 measures four failure modes live: position bias (swap the order and the winner changes), verbosity bias, prompt injection inside the graded text, and noise across runs.

Part 3 compares the judge with human labels, reads the disagreements, improves the judge prompt and measures again.

evals_03 · When an eval fails: call the model again

ScenarioWhat it shows
Unsupported replyRewrite with the policy, acting on the critique
Missing factsRepair the draft vs regenerate from scratch
Route by criterionA tone failure and a fact failure need different fixes
EscalateSwitch to a stronger model on failure
The loop that can't succeedWhy a limit and a fallback are mandatory
The judge is the problemA false alarm now changes what the customer reads

evals_04 · A full experiment

Hypothesis and metrics are written before running. A run passes only if it chose the expected action, included the required facts, included nothing forbidden, and the judge found it grounded and well-toned. Differences are tested with McNemar's test on paired cases and checked against bootstrap intervals.

Why this is a simulation: thirty invented cases written by the same author as the prompts say nothing about real traffic. In production the dataset comes from real, anonymised conversations, labelled by experts, and refreshed as traffic changes.

  1. In evals_02, swap the order in a pairwise comparison. Does the winner change?
  2. In evals_03, set the retry limit to 0. What does the customer see?
  3. In evals_04, add three harder cases to the dataset. Do the variants separate?

Takeaways

  1. Use code first; use a judge for what needs reading.
  2. Each check sees one thing. A grounded answer can be incomplete, and a polite one wrong.
  3. Measure the judge against human labels before trusting it.
  4. On retry, change the instruction, set a limit, and write the fallback first.
  5. Report uncertainty: intervals and paired tests, by segment, and weigh the cost.

Unit 6 · Guardrails · notebook guardrails_03

Execution: your strongest control point

Once a model can act, a wrong answer becomes a wrong action. Code in the gap between request and execution holds however the model was persuaded.

1

Least privilege

Offer only the tools this user and task need.

2

Arguments & business rules

Schemas check shape; rules check meaning: refund ≤ order value, own orders only.

3

Human approval

Pause high-risk actions, and keep them few enough that each gets read.

4

Budgets

Limit turns, tool calls and tokens, with a clear reason when one fires.

5

Indirect injection

Instructions hidden in tool results. Everything an agent reads is untrusted.

Rule

Identity from your system

Who the customer is comes from the login, never from the conversation or the model's arguments.

guardrails_03 · Execution

The agent loop from Unit 2 gains one hook: guard(name, arguments, run) is called before every tool. If it returns something, the tool does not run and the model receives that value instead.

def guard(name, args, run):
    if name not in ALLOWED_TOOLS[SESSION.role]:
        return "Not permitted."                      # least privilege
    if name == "issue_refund":
        order = ORDERS[args["order_id"]]
        if order.customer != SESSION.customer:       # identity from login
            return "Order not found."
        if args["amount"] > order.total:             # business rule
            return "Refund exceeds order value."
        if args["amount"] > 100:
            return queue_for_human(name, args)       # human approval
    if run.tool_calls >= 10:
        return "Tool budget reached."                # budget
    return None                                      # allowed

Illustrative sketch of the pattern; the notebook builds each check separately and tests it with forged calls, because a model behaving well today says nothing about the guard.

guardrails_04 · Output

Schema validation with retry (a Pydantic model checks an allowed category and priority), a sensitive-data leak filter, a groundedness check, a policy check, and a safe fallback. Well-behaved models rarely trigger these paths, so the notebook scripts bad drafts on purpose.

  1. In guardrails_02, write a message that a real customer might send but the scope filter blocks.
  2. In guardrails_03, forge a call to issue_refund for another customer's order. Which check stops it?
  3. In guardrails_04, script a draft that promises free shipping. Does the policy check catch it?

Takeaways

  1. A prompt is a request; a guardrail is enforcement.
  2. Three stages: before the model, around its actions, after its answer.
  3. Test with repeated runs and forged inputs. One clean run proves very little.
  4. Check evidence, not the model's account.
  5. Every check has a cost. Measure false alarms as carefully as catches, and judge a rare check by the cost of a miss.

For executives

Six questions to ask your team

Knowledge

Where do its facts come from?

Training, retrieved documents or live tools? Can we see the source behind an answer?

Reach

What can it touch?

Which tools and servers, with whose permissions? Who reviewed them?

Control

What can it do without a person?

Which actions need approval, and what are the limits in code?

Quality

How do we know it's better?

Which dataset, which metric, decided before the change? How good is the judge?

Failure

What happens when a check fails?

What does the customer see? Who is told? Is it logged?

Cost

What does each request cost?

Tokens, latency, extra calls for judges and retries, and false alarms.

Wrap-up

Five things to take home

  1. A model is not a system. Knowledge, tools, connections and procedures sit around it, in your code.
  2. The model requests, your code executes. That gap is where control lives.
  3. Skills guide, code enforces. Prompts shape tendencies; guardrails stop what must never happen.
  4. “Better” is a measurement, on a fixed dataset, with a judge you've checked.
  5. Every addition has a cost in tokens, latency, false alarms and new risks. Weigh it.
